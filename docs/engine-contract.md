# Engine contract v1

Issues #3, #11, #20 and #21 supply compile-ready contracts, deterministic command execution, setup/turn flow and self-contained decision fixtures for streams B/C. Import types, Zod schemas, `positionOf`, `createGame`, `applyAction`, `legalActions`, `observe`, `advanceAutomatically` and `replay` from `engine/index.ts`. Spec: v1.0 §3.1, §4.2, §6.1, §6.3, §6.4, §6.5, §6.6, §8; observations also follow §5.4.

## Records and counters

| Field | Meaning |
| --- | --- |
| `seatIndex` | Fixed, zero-based seat in turn order; distinct from actor identity and turn counters. |
| `globalTurnNo` | Number of turns started across all seats. |
| `Player.ownTurnNo` | Number of turns started for that player only. |
| `Player.routeProgress` | Signed whole number of squares travelled; `positionOf(p)` is `((p % 24) + 24) % 24`. |
| `Player.creditedLap` | Monotonic number of Start crossings already paid; it never decreases when movement goes backwards. |
| `GameState.stateRevision` | Number of accepted actions so far, initially 0. |
| `Action.actionSeq` | Starts at 1 and advances by exactly 1 for **every accepted action**, including engine-generated dice results, shuffles and event draws. |
| `Action.stateRevisionBefore` | Revision the actor saw; any value different from the current revision is stale. |

**Approved clarification (2026-10-07):** accepted actions, rather than turns or only player commands, determine both sequence and revision. The next accepted record has `actionSeq = stateRevisionBefore + 1`; the resulting revision equals its sequence. Rejection advances neither counter and changes no state. `actorId` is the configured player ID, or the reserved ID `engine` for generated records; `kind` discriminates `payload`. Do not configure a player with actor ID `engine`.

`GameConfig` records seats, seed, Lap target and engine/content/RNG versions. A seat may also specify `starterSpeciesId` to choose among its class's Starter alternatives. `GameState` embeds configuration and minimal content, players, active seat, phase, current budgets, optional Final Table Round target, private RNG cursor/state and private Event draw/discard piles. It contains **no nested log**. A fixture's separate `log` contains `{ action, events }` records. `EngineEvent` covers random results, sourced coin transfers (bank or player endpoints), UID creation/destruction, resolved spaces and phase changes. Pokémon and utility items each have `instanceId`; Balls use counted `poke`, `great`, `ultra` pouch entries. Pokémon record starter origin, evolution stage, tired status and ability readiness; items record public/secret visibility. Final Table Round records the triggering seat and target own-turn count, without implementing settlement.

## Public seam and visibility

Issue #11 adds pure RNG and version/header contracts (spec §4.6, §6.8, §8):

- `createRng(seed)` accepts a safe integer or nonempty string and returns `{ state, cursor: 0 }`. The current `RNG_VERSION` is exported from [engine/rng.ts](../engine/rng.ts); numeric seeds wrap to uint32 and string seeds use FNV-1a over UTF-16 code units. State is a canonical decimal uint32 string; helpers accept a safe nonnegative cursor below `Number.MAX_SAFE_INTEGER`. A final draw may return that maximum cursor, but it cannot be used as helper input again. Sequence/seed mapping/helper changes require a new version.
- `d6(rng, purpose?)`, `int(rng, n, purpose?)`, `weightedPick(rng, entries, purpose?)` and `shuffle(rng, input, purpose?)` return `{ value, rng, events }` without mutating input. Retain the returned `rng` for the next draw or snapshot; serializing it resumes the same sequence. `int` is zero-based with integer bounds 1 through 2^32. Weighted entries are `{ value, weight }`; weights must be finite, nonnegative and have a positive finite total.
- Every consumed draw returns `{ kind: 'random_result', purpose, result, drawCounter }`. Counters start at 1 and equal the resulting cursor. Dice/integers record their value; weighted picks record the selected entry index; Fisher-Yates shuffle records each swap's selected index in descending position order. Empty/singleton shuffles consume no draws. Invalid inputs throw `RangeError` without changing state. The historical issue #3 event schema allows omitted `drawCounter` for its unchanged illustrative fixtures; the new `RandomResultEvent` type always requires it.
- `createGameConfig(input)` stamps `ENGINE_VERSION`, existing `CONTENT_VERSION` and `RNG_VERSION`. `createLogHeader(config)` returns a detached header, preserving the supplied config's versions rather than replacing historical stamps. [engine/contract/schema.ts](../engine/contract/schema.ts) owns the `gameConfigSchema` and `logHeaderSchema` fields and validation, including header seed/version equality with the initial config. These helpers preserve historical stamps; the command-log executor below additionally checks that it supports the stamped engine and RNG versions.

- `applyAction(state, action: unknown): ApplyActionResult` validates untrusted command shape, current revision, next sequence, active configured actor and exact enabled choice (kind **and** payload). Rejection is `{ rejected: true, state, reason }` with the original state reference; reasons are `malformed_action`, `stale_revision`, `invalid_sequence`, `wrong_actor`, or `illegal_action`, checked in that order before player-choice membership. Acceptance is `{ accepted: true, state, events, record }` with a detached snapshot, resulting revision equal to the action sequence, and a separate `{ action, events }` record. The reserved engine identity takes the generated-record path after revision/sequence validation. Callers must retain the returned state and append the returned record to their separate log; no log is nested in state.
- `legalActions(state, seatIndex): LegalActions` returns stable-ID `{ id, kind, payload }` choices and disabled choices with `reasonCode`/English `reasonText`. Current-version games expose roll during first-player selection and Move, and skip during Start, Social, Strategy, Resolve and End. Pending dice results expose no player choice. Strategy is a pass-through stub even when a player owns items. Historical contract fixtures retain their illustrative item choices. Fixture-facing Encounter, Sell and Shop choices remain available, with their gameplay effects deferred. Target selection, budget spending, cooldowns, full-hand checks, combat, Gym, Abilities and social/deal/promise/chat execution remain deferred. Other phases return empty lists; out-of-turn seats receive only a disabled skip. IDs describe the same choice across repeated calls; records must still carry the current revision when submitted.
- `observe(state, seatIndex): Observation` explicitly projects public board, players' coins/positions/teams, utility-item counts, publicly visible utility items, Lap and ability readiness, phase and counters; `own` contains only that seat's utility items, Ball pouch and peek results. Opponent secrets, RNG state and Event order never appear. Returned observations are detached copies. Unknown seats throw `RangeError` in both read seams. Streams B/C should consume observations, not snapshots/logs; Jev's named buckets remain stream B's responsibility (§5.4).

**Approved Shop clarification (2026-10-08):** `shop-low-coins` retains 1 coin: Poké Ball is enabled at price 1, Great/Ultra Balls are disabled with `NOT_ENOUGH_COINS`. Added `shop-no-coins` uses 0 coins, disables all purchases and enables skip, demonstrating the all-unaffordable §3.1 row. Appendix A prices are unchanged.

## Content and fixtures

`Content` is the structural TypeScript contract inferred from exported `contentSchema` in [engine/contract/schema.ts](../engine/contract/schema.ts), the authoritative source for its fields and validation constraints. IDs join definitions to instances. This is the minimum fixture-facing interface, not a full effect/content catalogue; the content stream can provide additional data separately as later engine issues need it. The fixture validation test in [engine/fixtures.test.ts](../engine/fixtures.test.ts) checks the shipped content against this schema.

Each `engine/fixtures/*.json` contains `name`, full `state` (including fixture content), expected `legalActions` and `observation` maps keyed by seat index, plus a separate `log`. All include seat 0 and seat 1 projections. `fixtureSchema` validates their shapes; tests compare every expected projection/choice with the public functions. These are hand-authored snapshots, not an engine-generated replay or proof of implemented gameplay. `log-short` illustrates six contiguous accepted records; the executable command-log contract below is separate from these illustrative fixtures.

## Setup and turn flow (issue #21)

Spec: §3, §4.1, §4.2, §6.4. `createGame(config, content): GameState` validates and detaches both inputs, then constructs a revision-zero state before any first-player roll. It requires 2–4 unique actors/classes and fixed seats numbered 0 through n−1; input seat arrays are sorted by their configured indices, without changing seat identities. Engine and RNG stamps must be supported. Class, Starter and class-item references must exist in the supplied minimal contract content. A sole class Starter is selected automatically; alternatives require the seat's explicit `starterSpeciesId`, which must belong to that class.

Every player receives the starting kit and setup income defined in [spec §4.1](SPEC-v1.0-PokeMonopoly.md#41-setup-and-board), with route progress and credited Lap zero and an original base-form Starter. Ball class items go into the counted Ball pouch; utility class items receive distinct instance IDs and public visibility. Starter instance IDs are also distinct. Before play, all own-turn counters and the global counter are zero, and budgets are zero because no turn has started. The Event deck is empty until the later content/deck work supplies it; creation consumes no RNG.

Create the log immediately with `createGameLog(createGame(config, content))` and retain each subsequent returned record. `first_player_roll` carries the current contenders, completed rolls in that round and `awaitingResult`. Each configured contender, in seat order, accepts `roll`, then an engine `dice_result` with purpose `first-player:<seatIndex>`. No second player roll is enabled while awaiting the result. Once the round finishes, only tied highest rollers remain; their next round starts with no prior rolls. A unique leader starts the first turn. Every die result consumes one seeded draw, logs its counted random event and advances the accepted-action sequence separately from its roll command.

Starting a turn enters Start, increments `globalTurnNo` and only the active player's `ownTurnNo`, and **replaces** all three budgets with 1. The current skeleton is Start → Social → Strategy → Move → Resolve → End. The social window and Strategy pass through via the sole skip choice. Start/Resolve/End also use skip to drive the skeleton. Move accepts roll, waits for the engine result with purpose `move:<seatIndex>:<globalTurnNo>`, then enters Resolve. Every phase change emits `phase_changed`. Resolve does no space effect yet; no movement, Start crossing, passives, items, Abilities, chat or end-effect settlement is implemented by this issue. End starts the next configured seat, wrapping to seat zero after the last seat; the highest roller never reorders the seats.

The current engine stamp is owned by `ENGINE_VERSION` in [engine/versions.ts](../engine/versions.ts), and changed because accepted commands execute these new transitions. Unchanged historical `0.0.0` decision fixtures remain illustrative projections; they are not executable logs under the current version.

## Command log and replay (issue #20)

Spec: §3.1, §6.1, §6.3, §6.8, §8. The command pipeline now executes the setup/turn transitions above; other fixture-facing player commands still advance the accepted-action revision without gameplay effects. Movement, costs, catching, selling and other gameplay effects remain later rule issues. `roll` and its engine-generated `dice_result` are separate accepted records. The engine orchestration layer supplies generated records with actor `engine`; player/AI deciders must only submit player choices. Config schemas reject `engine` as a player ID.

Generated `dice_result` records verify `payload.value` against the next seeded `d6` for `payload.purpose`. The reserved `first-player:` and `move:` purposes additionally require the matching outstanding roll; wrong or repeated outcomes reject without consuming RNG. Other purposes retain the generic command-log draw behavior only outside first-player selection and when no roll result is pending. Generated `shuffle` records currently support `deckId: "events"` and verify `payload.order` against Fisher-Yates on the current draw pile, with purpose `shuffle:events`. Both retain the advanced RNG state and every counted `random_result` event. A shuffle is one action even when it consumes multiple draws, or no draws for an empty/singleton pile. Generated `event_draw` records must name the current first draw-pile entry; they move that entry to the discard pile without applying its game effect or consuming randomness. Invalid generated outcomes/deck IDs are `illegal_action`, and generated kinds submitted by a player are not enabled player choices.

`advanceAutomatically(state)` performs **one** acceptance step for an outstanding engine dice result, or when there is exactly one enabled player choice, returning `{ state, records, events }` and marking the record `auto: true`. Without an outstanding result, zero or multiple enabled choices return the original state with empty arrays. It has no decider argument and does not loop: the caller retains the returned state/log records and advances again to expose the next phase or decision. Roll and its generated result remain separate acceptance steps, including while resuming or replaying a pending roll. Disabled choices do not count toward the single-choice rule.

`GameLog` / `gameLogSchema` add `logVersion: "command-log-v1"`, `initialState` and ordered `actions: ActionRecord[]` to the existing versioned header. `createGameLog(initialState)` returns a detached, empty log. The explicit revision-zero snapshot preserves exact initial players, phase, content and deck without loading content via IO. New games use the pre-roll state from `createGame`; explicit revision-zero snapshots remain supported for contract scenarios. It must match `initialConfig` and its RNG must equal `createRng(seed)` at cursor zero. Headers retain the supplied content stamp and embedded content rather than substituting the current catalogue. The executor supports the current `ENGINE_VERSION` and `RNG_VERSION`; incompatible executors fail explicitly. Historical illustrative fixture RNG stamps/sentinel states are not executable logs.

`replay(log)` validates shape, header/snapshot consistency and supported versions, then runs each logged action through the same pure command boundary. It checks contiguous sequences, legality, every emitted event (including draw counters and outcomes), and any `auto` marker against the expected automatic step (pending engine result or sole enabled player choice). Invalid logs throw; the input log is never mutated. Seeded verification consumes the same recorded sequence, preserves its RNG cursor, and never calls a decider, network, storage or clock. The returned state can continue from its verified RNG state.

`stateHash(state)` is a pure TypeScript, non-cryptographic comparison aid: eight lowercase hex digits from FNV-1a over canonical JSON UTF-16 code units. Object keys are sorted lexically; array order matters. All state fields, including private RNG/deck/content, participate. Hash equality is useful in tests, not proof of authenticity or collision-free equality. A future change to executable effects must update the engine version and relevant rules/tests together; the log format and RNG have their own version stamps.

## Invariant checker (issue #14)

Spec: §1 (hard gates), §6.5, §8. `checkInvariants(before, action, result)` in [engine/invariants.ts](../engine/invariants.ts) takes the state and untrusted action passed to `applyAction` plus its result, and returns `Violation[]` (`{ invariant, message }`); an empty array means every active invariant held. It is pure, deterministic and imports only `engine/` modules. `INVARIANTS` registers every spec §8 invariant by ID with its section, the exact spec line, and `active` or `pending` status; pending invariants switch on when their rules land. Active this cycle: non-negative coins, sourced `coin_transfer` events that account for every coin change, unique instance IDs across teams, items and the current encounter's Pokémon, a logged `uid_created` or `uid_destroyed` for every team or item instance that appears or vanishes (an instance ID is created at the catch, per issue #23, so the wild encounter's Pokémon is in the uniqueness check only), unchanged state hash after a rejected or stale action, exactly 1 Ball per catch and none per release, monotonic `creditedLap` that never exceeds the milestone reached (the §6.5 payment half, no Start income for a re-crossed milestone, is registered `pending` until `coin_transfer` events carry an agreed Start-income reason code), step replay that reproduces the logged state and events, and an unfinished game whose active seat always has an enabled choice. `createInvariantChecker(applyActionFn)` builds the same checker against another engine function, which tests use to model a deliberately broken engine. The sim runner from issue #13 is to call it after each action through a one-line hook, wired once both issues have merged. Until issue #23 makes catches spend a Ball, the fixture sweep skips catch choices, and a test that fails once catches spend a Ball marks the carve-out for removal.
