# ai/

Server only. This is the only place `TYPESAFE_API_KEY` lives. It validates payload shape and size, builds questions from role-scoped state, calls Jev and returns only action IDs and line IDs.

`jev/client.ts` is the only code that touches the SDK. The rest of `ai/` depends on its `JevClient` interface, which pins `jev-1.13.0`, enforces the §5.6 deadlines, never retries and turns every unusable answer into a `fallbackReason`. Tests use `jev/fake.ts` or the real wrapper with a placeholder key and a fake `fetch`; `JEV_ENABLED=false` needs no key at all.

Routes (`app.ts`): `POST /api/ai/decide` takes a `DecisionRequest` (at most 32 KB, strict zod: unknown fields, including any in the observation, are a 400) and returns a `DecisionResponse` with only an action ID (or `sellUids` at the Sell Phase) and telemetry. `GET /api/ai/status` returns `{ jevEnabled, backupOnly, reason }` for the backup-bot badge; `reason` is `disabled` (kill switch), `missing_key` or `budget_exceeded` (spend guard). Both shapes live in `engine/contract/decision.ts`, so `web/` imports them without importing `ai/`. `decide` calls a pluggable `Decider` (`decider.ts`), by default `createOrchestratorDecider`: one `Orchestrator` per `gameId` from a bounded cache (`MAX_CACHED_GAMES`, 64, least recently used out; an evicted game starts its per-turn request count and per-game token budget again), so the 1,500 ms decision deadline and the 3 requests per `turnKey` hold across requests. The Jev client is made on the first decision that can use it, and only when `JEV_ENABLED` is on, `TYPESAFE_API_KEY` is set and the spend guard is not tripped. Otherwise the `FallbackPolicy` (Greedy unless `personalityId` names another installed personality) decides and the status reason is reported as `fallbackReason` (`disabled`, `missing_key`, `budget_exceeded`), without any request. The `facts.catchOdds` in the request feed the Encounter question and the policy; the wire carries no Sell facts yet, so a Sell Phase falls back with `missing_facts`. Hard plays as Normal until gate G2. Orchestrator outcomes map onto the wire: `jev` stays `jev`; `fallback` keeps its reason (the client's, plus `invalid_choice`, `revision_mismatch`, `low_confidence`, `request_limit`, `token_budget`, `missing_facts`); `auto` (no question asked, such as one legal action) becomes `fallback` with reason `auto`. The orchestrator's log `events` stay server-side. Any answer that is not among the enabled options is still replaced by the first enabled action (spec §3.1), and a decider that throws (`decider_error`) does the same. The `/api/ai/fallback` route (the browser's answer at its own 1,500 ms deadline) returns the `FallbackPolicy` choice. The web shows the Backup bot badge and banner only for unavailability reasons (`disabled`, `missing_key`, `budget_exceeded`, `timeout`, `network`, `rate_limited`, `server_error`, `auth`); `auto`, `low_confidence` and the other decision-level reasons are normal play.

The additive `shop.ts` request variant accepts `decisionPoint: "shop"` without changing the
engine's Strategy/Encounter/Sell contract or the pluggable stub decider. It checks seat,
active seat, revision, phase, unique enabled action IDs and strict role-scoped observation
shape. Shop has no Jev question (§5.2, §5.3): the existing `FallbackPolicy` chooses among
enabled options with `createPolicyRng`, seeded by the opaque game ID, turn key and revision.
Retries of the same decision therefore return the same choice without touching the
engine's private RNG. This interim C2 path uses the installed Greedy personality and returns
only the usual action-ID/fallback telemetry response; `shop.test.ts` covers legal choices,
determinism and invalid role-scoped requests. Orchestrator work (#45) and AI turn presentation
(#50) extend or supersede this interim web handoff.

`orchestrator.ts` is the decision orchestrator (spec §3.1, §5.3, §5.6, §6.8, §9). Create one `Orchestrator` per game with a `JevClient`; `decide(request)` takes the seat's observation, legal actions, engine facts, difficulty, personality and a seeded `PolicyRng`. Strategy and Encounter become one bundled Choice request and the Sell Phase one Noul per offered Pokémon (up to 12 per request); phases without a Jev question and single-action decisions are chosen by the fallback policy as `source: 'auto'`. One 1,000 ms request and 1,500 ms decision deadline apply; the decision returns at the deadline and a late answer is never applied. Nothing is retried. Every unusable answer falls back to the fallback policy with a `fallbackReason`: the client's (`timeout`, `rate_limited`, `server_error`, `auth`, `network`, `schema_mismatch`, `disabled`), `invalid_choice` (not among the options), `revision_mismatch` (`currentRevision()` moved while waiting), `request_limit` (3 requests per AI turn, keyed by `turnKey`), `token_budget` (600,000 input tokens per game, from the `UsageMeter`), `budget_exceeded` (the spend guard below), `missing_facts` (the Encounter odds or Sell facts were not given; the sim has no engine keep value yet, so its Sell Phases use the fallback) and `low_confidence`. Easy samples Jev's `probabilities` with one seeded draw out of 2^32, logged as `sampled`; Normal takes the highest probability and, below `confidenceFloor(type, optionCount)` (`ORCHESTRATOR_CONFIG`: 0.6 up to 4 options, falling to 0.5 at 12, untuned until cycle 4), lets the fallback policy choose between Jev's top two. Each decision returns `events` `{requestId, model, questionId, choice, probabilities, confidence, sampled, fallbackReason}` for the caller to append to the game log; replay never calls Jev. `DecisionStats` and `decisionRates` give `invalidOutputRate` and `fallbackRate` by cause. `jev-policy.ts` registers the sim's `--policy jev` with one orchestrator per game; `jev/fake.ts` holds the seeded chaos client it uses offline.

`jev/spend.ts` is the §9 spend guard. `SPEND_CONFIG` is the only place the input price ($0.042 per million tokens, output free), the assumed 33 THB/USD and the THB 1,500 total cap live. An orchestrator given a `usage` recorder writes one line per request that went out to `logs/jev-usage.jsonl` (git-ignored): `time`, `gameId`, `requestId`, `model`, `inputTokens`, `outputTokens`, `latencyMs`, `status` (`ok` or the client's fallback reason), `turnKey`, `decision` (its number in the game) and `decisionMs`. An answer that arrived but failed validation, or arrived after the deadline, counts the tokens it reported; a timed-out request with no reported usage counts `SPEND_CONFIG.estimatedInputTokensPerRequest` (3,240, the #5 spike's measured average) and its line carries `estimated: true`, so the cap and the per-game token budget err on the safe side. A line holds no state, question text or key. `SpendLedger` adds up THB from every earlier line of the log plus each new one, warns once at 80% of the cap, and reports the budget exceeded at the cap or once today's spend (UTC) reaches `JEV_DAILY_BUDGET_THB` when that is set; from then on every decision falls back with `budget_exceeded` before any request goes out, and the status endpoint says so. Only the real service is guarded and logged: the sim's chaos fake and `JEV_ENABLED=false` write nothing. `npm run usage [-- --log <file>]` (`jev/usage-cli.ts`) prints requests, tokens, USD, THB, the share of the cap (with the number of estimated requests), today's spend and AI decision time per turn p50 and p95 (a turn adds each of its decisions once).

`questions/` builds each decision point's Jev questions from role-scoped state (Strategy, Encounter and the Sell Phase Nouls); see `skills/jev-questions`.

`fallback/` is the §5.2 fallback policy: personality-weighted utility over the enabled actions, from the seat's `Observation` plus engine `PolicyFacts` only. `FallbackPolicy` implements the sim's `Policy` (`npm run sim -- --policy fallback`), and `decideWithFallback` applies Jev's choice at or above the confidence floor and otherwise picks between Jev's top two by personality weight (§5.6). Personalities load from `content/personalities/*.json` through `content/personality-schema.ts`.

`lines.ts` holds the validated English line bank (`content/lines/en/`). `selectLine(situation, personalityId, trustBucket, rng)` picks a line uniformly with the seeded engine RNG, returns its line ID and template with the new RNG state, and returns a `line_selected` event alongside the draw. Callers append these events to `GameLog.dialogueEvents`, which survives save/load. Use a separate presentation RNG and retain its returned state for subsequent line selections; gameplay RNG and command replay are unaffected. Gameplay display wiring is deferred to later work; the engine fills the template's slots with `fillSlots` (spec §5.7).

No hidden information goes in: send only what that seat can see. Must not import from `web/`; lint enforces this. The browser reaches it through `/api` (port 8787; Vite proxies in dev).

Spec: §3.1, §5.2, §5.3, §5.4, §5.5, §5.6, §5.7, §6 item 2, §6 item 8, §9. Skill: `skills/jev-questions`.
