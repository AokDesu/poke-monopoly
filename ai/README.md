# ai/

Server only. This is the only place `TYPESAFE_API_KEY` lives. It validates payload shape and size, builds questions from role-scoped state, calls Jev and returns only action IDs and line IDs, plus, on `POST /api/ai/speak`, one screened line of speech.

`jev/client.ts` is the only code that touches the SDK. The rest of `ai/` depends on its `JevClient` interface, which pins `jev-1.13.0`, enforces the §5.6 deadlines, never retries and turns every unusable answer into a `fallbackReason`. Tests use `jev/fake.ts` or the real wrapper with a placeholder key and a fake `fetch`; `JEV_ENABLED=false` needs no key at all.

Sell facts (#150): the browser sends `facts.sell`, the engine's `saleFacts` rows (`instanceId`, `salePrice`, `classBonusAlone`, `classBonusTogether`, `saleValue`, `keepValue`; strict, no other field) for every Pokémon on the team. `decider.ts` accepts them only when they cover exactly the sellable Pokémon, then maps them to the orchestrator's `SellFacts` (so Jev is asked one Noul per Pokémon, with separate `sale_value_now`, `keep_value` and `class_bonus` buckets) and to the fallback policy's `saleValue` and `keepValue`. Keep value is the loss of the team's highest battle-ready current-form Battle stat when that Pokémon is removed: low at 0, medium at 1–2, high at 3+ (spec §5.4/§5.6). It is Battle points, never coins or an evolution/future-sale forecast. Missing, partial or foreign rows fall back as `missing_facts`.

Routes (`app.ts`): `POST /api/ai/outcome` (below) and `POST /api/ai/decide` takes a `DecisionRequest` (at most 32 KB, strict zod: unknown fields, including any in the observation, are a 400) and returns a `DecisionResponse` with only an action ID (or `sellUids` at the Sell Phase) and telemetry, plus a `detail` (`decisionDetailSchema`: question, confidence or null at the Sell Phase, per-option probabilities) only when `DEMO_MODE` is on and Jev decided. `GET /api/ai/status` returns `{ jevEnabled, backupOnly, reason, speech, demo }` (`demo` is the server's `DEMO_MODE`, exactly `1` or `true`; never taken from a request) for the backup-bot badge; `reason` is `disabled` (kill switch), `missing_key` or `budget_exceeded` (spend guard). Both shapes live in `engine/contract/decision.ts`, so `web/` imports them without importing `ai/`. `decide` calls a pluggable `Decider` (`decider.ts`), by default `createOrchestratorDecider`: one `Orchestrator` per `gameId` from a bounded cache (`MAX_CACHED_GAMES`, 64, least recently used out), over a separate per-game `GameQuota` that holds the game's input-token budget, its Jev requests per `turnKey` and its decision numbers for the usage log. A quota is a few counters and is never evicted while the server runs (a restart starts over; the spend ledger on disk still caps spend across restarts), and at most `MAX_TRACKED_TURNS` (2,000) turns of one game are tracked, a further turn being refused rather than counted afresh. Dropping an idle orchestrator therefore never hands its game a fresh budget or restarts its decision numbers, and a `turnKey` keeps its count when a game returns to it (the cap is 3 per `turnKey`, whatever order the turns arrive in, concurrent or not). The 1,500 ms decision deadline holds in every request. The Jev client is made on the first decision that can use it, and only when `JEV_ENABLED` is on, `TYPESAFE_API_KEY` is set and the spend guard is not tripped. Otherwise, and when the client cannot be made (reason `decider_error`), the `FallbackPolicy` (Greedy unless `personalityId` names another installed personality) decides and the status reason is reported as `fallbackReason` (`disabled`, `missing_key`, `budget_exceeded`), without any request. The `facts.catchOdds` in the request feed the Encounter question and the policy; the `facts.sell` rows (the engine's `saleFacts`, covering every sellable Pokémon) feed the Sell Nouls and the policy's sale values, and a Sell Phase falls back with `missing_facts` only when those rows are missing, partial or foreign. Hard (spec §5.6) adds the engine's Monte Carlo rollout buckets to each Strategy and Encounter option (`hard.ts`, from `engine/rollout.ts`, which reads only the seat's observation), within a 400 ms limit taken off the decision deadline, and plays as Normal when there are none. Orchestrator outcomes map onto the wire: `jev` stays `jev`; `fallback` keeps its reason (the client's, plus `invalid_choice`, `revision_mismatch`, `low_confidence`, `request_limit`, `token_budget`, `missing_facts`); `auto` (no question asked, such as one legal action) becomes `fallback` with reason `auto`. Each decision's §6.8 `events` are written, never returned, and only for the outcome the browser applied. The browser tells the server what it applied with `POST /api/ai/outcome` (IDs only: the decision's `gameId`, `seatIndex`, `turnKey`, `stateRevision`, `decisionPoint`, the `choice` or `sellUids`, and `source` and `fallbackReason`), because it applies its own fallback with `timeout` when the answer is late, however long the server took. `jev/decision-journal.ts` holds each answer the server gave until the report arrives, in either order, and then logs the server's events when the browser applied that answer, or one event for the outcome the browser used when it did not (for example `skip` with `timeout` where the server's late answer was `use-item:item-0`). The fallback the browser prepares in parallel (`/api/ai/fallback`) is never a decision and is never logged. The server (not `createApp()` by default, so tests write nothing) appends the events to `logs/jev-decisions.jsonl` (git-ignored; `jev/decision-log.ts`) as `time`, `gameId`, `seatIndex`, `turnKey`, `stateRevision`, `decisionPoint`, `requestId`, `model`, `questionId`, `choice`, `probabilities` (keyed by action ID), `confidence`, `sampled` (Easy's draw out of 2^32) and `fallbackReason`, from an explicit field list, so no state, question text or key can reach it. A decision the fallback policy made without the orchestrator logs one event with its reason. A decision whose report never arrives (a closed tab) is dropped unlogged once more than 1,024 are waiting. The file is appended in the background (its folder made whenever it is missing, so removing `logs/` while the server runs is fine), never awaited by a decision; a log that fails never fails or delays a decision and warns once. Any answer that is not among the enabled options is still replaced by the first enabled action (spec §3.1), and a decider that throws (`decider_error`) does the same. The `/api/ai/fallback` route (the browser's answer at its own 1,500 ms deadline) returns the `FallbackPolicy` choice. Which reasons light the web's Backup bot badge and banner, and which show a §3.1 per-turn note instead, is spec §3; the `fallback_notice` line header (`presentation.ts`) follows the same unavailability rule.

The additive `shop.ts` request variant accepts `decisionPoint: "shop"` without changing the
engine's Strategy/Encounter/Sell contract or the pluggable decider. It checks seat,
active seat, revision, phase, unique enabled action IDs and strict role-scoped observation
shape. Shop has no Jev question (§5.2, §5.3): the existing `FallbackPolicy` chooses among
enabled options with `createPolicyRng`, seeded by the opaque game ID, turn key and revision.
Retries of the same decision therefore return the same choice without touching the
engine's private RNG. This interim C2 path uses the installed Greedy personality and returns
only the usual action-ID telemetry response, with `fallbackReason: 'auto'` (no Jev question was asked;
never `stub`). The decision is journalled like any other: `app.ts` proposes it on `decide` and the
browser's `/api/ai/outcome` (decision point `shop`) completes it, so the decision log holds one
non-Jev row, `questionId: "shop"`, `fallbackReason: "auto"`, for every Shop decision. When the
browser's deadline passes first, the applied row is `timeout` or `network` instead, so a fallback-rate
report built from the decision log must skip rows whose `decisionPoint` is `shop`: Shop has no Jev
question, so it is never a Jev fallback (the §5.6 rates from `DecisionStats` already exclude it). `shop.test.ts`
covers legal choices, the log row,
determinism and invalid role-scoped requests. Orchestrator work (#45) and AI turn presentation
(#50) extend or supersede this interim web handoff.

`orchestrator.ts` is the decision orchestrator (spec §3.1, §5.3, §5.6, §6.8, §9). Create one `Orchestrator` per game with a `JevClient`; `decide(request)` takes the seat's observation, legal actions, engine facts, difficulty, personality and a seeded `PolicyRng`. Strategy and Encounter become one bundled Choice request and the Sell Phase one Noul per offered Pokémon (up to 12 per request); the `promise_response` point is one accept or reject Choice (`questions/promise.ts`, fallback scored by loyalty and trust in `fallback/policy.ts`), while `deal_response` is still `auto`; phases without a Jev question and single-action decisions are chosen by the fallback policy as `source: 'auto'`. One 1,000 ms request and 1,500 ms decision deadline apply; the decision returns at the deadline and a late answer is never applied. Nothing is retried. Every unusable answer falls back to the fallback policy with a `fallbackReason`: the client's (`timeout`, `rate_limited`, `server_error`, `auth`, `network`, `schema_mismatch`, `disabled`), `invalid_choice` (not among the options), `revision_mismatch` (`currentRevision()` moved while waiting), `request_limit` (3 requests per AI turn, keyed by `turnKey`), `token_budget` (600,000 input tokens per game, from the `UsageMeter`), `budget_exceeded` (the spend guard below), `missing_facts` (the Encounter odds or Sell facts were not given; the sim's `--policy jev` does not pass Sell facts yet, so its Sell Phases use the fallback) and `low_confidence`. Easy samples Jev's `probabilities` with one seeded draw out of 2^32, logged as `sampled`; Normal takes the highest probability and, below `confidenceFloor(type, optionCount)` (`ORCHESTRATOR_CONFIG`: 0.6 up to 4 options, falling to 0.5 at 12, untuned until cycle 4), lets the fallback policy choose between Jev's top two. Each decision returns `events` `{requestId, model, questionId, choice, probabilities, confidence, sampled, fallbackReason}` for the caller to append to the game log; replay never calls Jev. `DecisionStats` and `decisionRates` give `invalidOutputRate` and `fallbackRate` by cause. `jev-policy.ts` registers the sim's `--policy jev` with one orchestrator per game; `jev/fake.ts` holds the seeded chaos client it uses offline.

`jev/spend.ts` is the §9 spend guard. `SPEND_CONFIG` is the only place the input price ($0.042 per million tokens, output free), the assumed 33 THB/USD and the THB 1,500 total cap live. An orchestrator given a `usage` recorder writes one line per request that went out to `logs/jev-usage.jsonl` (git-ignored): `time`, `gameId`, `requestId`, `model`, `inputTokens`, `outputTokens`, `latencyMs`, `status` (`ok` or the client's fallback reason), `turnKey`, `decision` (its number in the game) and `decisionMs`. An answer that arrived but failed validation, or arrived after the deadline, counts the tokens it reported; a timed-out request with no reported usage counts `SPEND_CONFIG.estimatedInputTokensPerRequest` (3,240, the #5 spike's measured average) and its line carries `estimated: true`, so the cap and the per-game token budget err on the safe side. A line holds no state, question text or key. `SpendLedger` adds up THB from every earlier line of the log plus each new one, warns once at 80% of the cap, and reports the budget exceeded at the cap or once today's spend (UTC) reaches `JEV_DAILY_BUDGET_THB` when that is set; from then on every decision falls back with `budget_exceeded` before any request goes out, and the status endpoint says so. Only the real service is guarded and logged: the sim's chaos fake and `JEV_ENABLED=false` write nothing. `npm run usage [-- --log <file>]` (`jev/usage-cli.ts`) prints requests, tokens, USD, THB, the share of the cap (with the number of estimated requests), today's spend and AI decision time per turn p50 and p95 (a turn adds each of its decisions once).

`haiku/` is the speech writer's server-side client (spec §5.2, §9); `speech/speak.ts` is its only caller. `haiku/client.ts` is `createHaikuClient`, the only code that talks to Haiku: plain `fetch` to `https://api.anthropic.com/v1/messages`, the pinned model `claude-haiku-5-5`, thinking off at low effort, an 80-token output ceiling, no streaming, no retries, `redirect: 'error'`, a 16 KiB response cap and a 3,000 ms deadline (`HAIKU_DEADLINE_MS`; issue #214: table talk may wait about 3 s, a decision keeps Jev's own deadlines) after which a late answer is discarded. `write(request)` never throws; it returns the text and billed usage, or a fallback reason: `disabled` (`HAIKU_ENABLED` is not `true`), `missing_key` (`ANTHROPIC_API_KEY` unset or not one printable ASCII value), `budget_exceeded` (Haiku's THB 150 cap or the THB 1,500 total is reached), `timeout`, `network`, `rate_limited` (429), `server_error` (5xx, and any other non-200), `auth` (401, 403), `refused` or `unsafe_response` (oversized, malformed, cut off, a model other than the pinned one, or a body containing the key). The first three send nothing and log nothing. Every request that goes out writes exactly one `logs/jev-usage.jsonl` line with `provider: "haiku"` (Jev lines have no provider), the reported token counts, and for a timeout or an unreadable reply the configured estimate (`estimatedHaikuInputTokensPerRequest`, `estimatedHaikuOutputTokensPerRequest`) with `estimated: true`; it never holds a prompt, a line of speech or a key. `SPEND_CONFIG.haikuModelPrices` holds the per-model prices ($0.10 in, $0.50 out per million tokens); `SpendLedger.budgetExceeded('haiku')` is the Haiku-only stop and warns once at 80% of it. The daily budget counts Jev only. `haiku/status.ts` reads `HAIKU_ENABLED` and `ANTHROPIC_API_KEY` (only `ai/` may) and fills the `speech` field of `GET /api/ai/status`: `{ enabled, reason }` with the same reasons. `haiku/fake.ts` serves tests; `sim/` and `eval/` cannot import `haiku/` (lint, `jev/key-scope.test.ts`), so replay and simulation never call Haiku.

`speech/speak.ts` and `POST /api/ai/speak` (spec §3.1, §5.6, §5.7, §6 item 2, §9; issues #172, #214) are the first route that returns text. The request is strict zod, at most 16 KB (oversized is a 400): `gameId`, `seatIndex`, `stateRevision`, the speaker's own `observation`, a line-bank `situation`, an optional `addressedSeat`, `personalityId` and `turnKey`; an unknown field, a seat or revision that does not match the observation, a situation without a topic in `content/voice/en.json`, an unknown personality or an addressed seat that is not another seat at the table is a 400. Every line-bank situation but `fallback_notice` has a topic, so table talk can speak about a roll, a catch, a battle, a payment, a sale, a Gym win or nothing in particular (`table_banter`), about its own turn (`*_own`) or another seat's (`*_other`). The speaker builds the public brief (no recent events yet: the request carries none), calls the `HaikuClient` and answers within one 3,000 ms deadline: `{ source: 'haiku', text }` for a reply that passes the output screen, otherwise `{ source: 'bank', text, lineId, fallbackReason }` (the bank template with its `{slot}`s unfilled, picked with a presentation RNG seeded by game, turn, revision and seat) or `{ source: 'none', fallbackReason }` when the personality has no line. Past a valid request every failure is still a 200; the reason is one of the client's, an output-screen rejection, or `call_limit`, `token_limit`, `in_flight`, `game_limit`, `internal_error`. Each game's limits (150 calls, 200,000 input tokens, one call in flight; `SPEND_CONFIG`) live in a small per-game counter that is never evicted, and at most `MAX_SPEECH_GAMES` games are tracked, so a game cannot reset its own count; the browser keeps a game's ID across a reload so the count carries on; a call counts when it settles, even after the deadline, so a late answer's tokens still count (its usage line is the client's, with the configured estimate for a timeout). The shared Haiku and total caps are read first through `speechStatus`: when speech is off, past the cap or over a game limit, no request is made. Output-screen rejections are counted by reason and logged as `Speech line rejected: <reason> (<n> so far).`, never with the text. `speech/guard.ts` makes the route same-origin only: Host must be loopback (`localhost`, `127.0.0.1`, `[::1]`) and Origin the same host (Vite's dev proxy keeps its own port), else 403; any content type but JSON is 415; both are checked before the body is read. `npm run speech:smoke` (`speech/smoke.ts`) is the owner-run live check: it sends three fixed briefs through the same speaker with the real key, `--rounds` times (default 4, so 12 calls), and prints each line, tokens, baht and latency with p50 and p95; a coding agent never runs it. `GET /api/ai/status` already carries `speech: { enabled, reason }`.

AI-to-AI replies (spec §4.2, §5.3, §5.7, §9; issues #177, #214): `POST /api/ai/speak` with `kind: 'reply'` (`replyRequestSchema` in `engine/contract/speech.ts`: the listener's `seatIndex` and `observation`, the `speakerSeat`, the `quote` of at most 200 characters, a `situation` (the browser sends `table_retort`), `personalityId` and `turnKey`; same-origin and 16 KB limits as above) is the second half of an exchange. `Speaker.reply` checks the request like `speak`, re-screens the quote with the output screen (a line that could never have been shown is not quoted, and costs nothing), then asks `speech/gate.ts`'s `ManipulationGate` (the question and the verdict rule are in `questions/manipulation.ts`, the same question the player's chat reply asks in `chat-reply.ts`): one Jev request, 1,000 ms, whose state is the quoted line with its speaker's class name and nothing else, logged as one Jev usage line and refused when Jev's budget is spent. A Noul at or above `CHAT_TUNING.manipulationThreshold`, the chat reply's own threshold, is `manipulation`; any answer that is not the Noul, a timeout, a spent budget or a client that cannot be made is `gate_unavailable`: the gate fails closed. Only then does the listener's Haiku prompt carry the line, as `reply_to` data in the brief under the same instruction, deadline, per-game limits (the reply is one of the game's 150 calls, and Haiku's own cap, the per-game calls, tokens and in-flight limits are checked before Jev is asked) and output screen. The answer is `{ source: 'haiku', text }` or `{ source: 'none', fallbackReason }`, never a line-bank line, and never the quote; the browser answers a refused or late exchange from the line bank itself (`table_retort`), which never reaches this route. `speech/fixtures/exchange-gate.json` holds the 27 adversarial and 7 clean lines with hand-written stand-ins for recorded Jev answers (its `provenance` says so); `speech/exchange.test.ts` runs them offline with `jev/fake.ts` and `haiku/fake.ts`.

Chat replies in the rival's own words (spec §4.8, §5.7, issue #178): `POST /api/ai/speak` with `kind: 'chat_reply'` (`chatSpeechRequestSchema` in `engine/contract/speech.ts`: the rival's `seatIndex` and `observation`, the `addressedSeat` (the human who wrote), the message's `topic`, the `decision` (`noncommittal` or `refused`, the one the chat route already made), `personalityId` and `turnKey`; same-origin and 16 KB limits as above; a strict schema, so there is no field for free text) is answered by `Speaker.chatReply`. The brief is the public speech brief for the situation the decision belongs to (`chat_reply` or `manipulation_refused`) plus `chat_reply`: team-written words for the topic raised and the decision taken (`speech/chat.ts`), never the item or leader a message named and never a quote. The reply goes through the same kill switches, per-game limits, deadline and output screen as a line; it must also not repeat the card it was given and must not say the opposite of the decision (`contradictsDecision`: assent for either decision, refusal for a noncommittal one, openness for a refusal), which is dropped as `contradiction`. The answer is `{ source: 'haiku', text }` or `{ source: 'none', fallbackReason }`, never a bank line: the browser already holds the chat route's own line. No manipulation question is asked, as there is nothing quoted. The words never choose the decision, change a number or reach another seat.

`questions/` builds each decision point's Jev questions from role-scoped state (Strategy, Encounter and the Sell Phase Nouls); see `skills/jev-questions`.

`fallback/` is the §5.2 fallback policy: personality-weighted utility over the enabled actions, from the seat's `Observation` plus engine `PolicyFacts` only. `FallbackPolicy` implements the sim's `Policy` (`npm run sim -- --policy fallback`), and `decideWithFallback` applies Jev's choice at or above the confidence floor and otherwise picks between Jev's top two by personality weight (§5.6). Personalities load from `content/personalities/*.json` through `content/personality-schema.ts`.

`lines.ts` holds the validated English line bank (`content/lines/en/`). `selectLine(situation, personalityId, trustBucket, rng)` picks a line uniformly with the seeded engine RNG, returns its line ID and template with the new RNG state, and returns a `line_selected` event alongside the draw. Callers append these events to `GameLog.dialogueEvents`, which survives save/load. Use a separate presentation RNG and retain its returned state for subsequent line selections; gameplay RNG and command replay are unaffected. Gameplay display wiring is deferred to later work; the engine fills the template's slots with `fillSlots` (spec §5.7).

`speech/` is the pure half of Haiku-written table talk (brief, screen and bank pick are pure: no network, no key; `speak.ts` below adds the call). `buildSpeechBrief` turns the speaking seat's observation, the events of its own feed and a line-bank situation into public facts only: names, standing as `leading`/`level`/`behind`, a Lap stage, up to three recent public events without amounts, the personality text, a class hint and the world card from `content/voice/en.json`. It is stricter than `buildJevState`: never the seat's items, Balls or peek results, chats, the seed or the deck order, and never a digit; it runs the same `assertNoComparableNumbers` and size guards. `screenSpeech` accepts a reply only if it is one plain paragraph of 1 to 140 characters with no digit, number word, link, markup, quotation mark, utility item that is not public in the brief, species outside the content, offer or promise wording, probe for hidden things or echo (five words in a row) of the instruction or the brief's text. `resolveSpeech` returns the accepted line, otherwise a line-bank pick with the presentation RNG, or silence when the personality has no line for the topic; nothing is ever invented. `SPEECH_INSTRUCTION` is the team-written system instruction. Tests use recorded replies in `speech/fixtures/`.

No hidden information goes in: send only what that seat can see. Must not import from `web/`; lint enforces this. The browser reaches it through `/api` (port 8787; Vite proxies in dev).
